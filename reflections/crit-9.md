**What was the breakthrough that moved the work forward?**

Not the networking (that was already settled by the earlier shared-arena work) — it was noticing that "a room" isn't one setting, it's three different questions wearing one checkbox each: can you *see* a room exists, can you *watch* it, can you *become a Player* in it. The brief's own example made `locked` sound like it should gate everything, but working through the locked-room case explicitly — "a locked room must still admit Viewers when its creator allows it" — only resolves cleanly if lock/viewer/capacity are three independent checks, not one combined flag. Writing that out as ADR-002's actual decision, rather than letting the first implementation that compiled decide it implicitly, is what kept the lobby's preview authorization, the role-selector's enable/disable logic, and the server's join validation all agreeing with each other instead of drifting apart.

The second breakthrough was adversarial, and came from my own review before any test ran: an early version of the "join a room" logic treated every join as "leave wherever you are, then join the new place" — which is correct for joining a *different* room, but wrong for a creator switching their own role inside the room they created, because "leaving" a room you created is exactly the trigger that closes it. The bug was real (the creator closing their own room by clicking "Become Player" after "Become Viewer") and it was never an observed test failure — it's the kind of thing that only shows up once someone (or something) runs the exact sequence "creator becomes viewer, then becomes player again," which none of my first-draft tests happened to do.

Catching this changed how I interpret a green test result. Passing tests are evidence that the tested cases behave as expected, not proof that the design is correct. I need to ask which sequences the tests actually cover, especially when one action changes the state that another action depends on. In this case, reading through the lifecycle logic and mentally tracing the creator's role-switching sequence exposed a bug that a happy-path test could easily miss. That review was not a substitute for testing; it showed me which regression test needed to exist.

**What did this work change about who I want to be as a software developer?**

I want to become a developer who treats access rules and state transitions as part of a feature's correctness, rather than details to polish after the feature appears to work. Building the room lobby made this distinction concrete: showing a room in a list, allowing someone to watch it, and allowing them to play are separate permissions, and each must remain consistent across the interface and the server. A successful demo of the normal path would not establish that consistency.

The creator role-switching bug also reinforced that I cannot delegate all correctness checks to the test suite or to a coding agent. An implementation can look reasonable, compile, and pass its existing tests while still violating an important invariant. I want to get better at reviewing changes by tracing state transitions, identifying assumptions, and testing unusual but valid sequences—not just asking whether the feature works once. Using an agent is valuable when it helps me implement and investigate faster, but I still need to understand the decisions well enough to challenge the first plausible solution and explain why the final behaviour is correct.
